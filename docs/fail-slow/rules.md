# Probing Fail-Slow 实验规则

> **这份文档是什么**：跑 Probing fail-slow 实验时**不会变的方法论**——红线、控制变量原则、三阶段各自该做什么。写一次，很少动。
>
> **谁看**：任何要执行、审阅、复现这套实验的人或 Agent。纯 markdown，Claude / Cursor 都能直接读，可打包发人。
>
> **和台账的分工**：本文件只讲“怎么做才严谨”。**具体用什么模型、开了什么、哪个集群会怎么崩——全在 [`ledger.md`](ledger.md)**，那份由执行的 Agent 边跑边维护。本文件里**不写任何**集群名、镜像名、环境变量的具体值。
>
> **上位规程**：[`sop.md`](sop.md) 是更长的完整规程；本文件是它的“可执行内核”。两者冲突时，以本文件的红线为准。

---

## 一、红线（六条，任何时候都不许破）

1. **不改训练代码。** 工具（Probing 或对手）只走环境变量 / LD_PRELOAD / attach 接入。训练脚本对“有没有注入”“有没有在检测”**完全无感知**——不许为了帮检测在训练里加 hook / print / barrier。

2. **检测方案里不准出现答案。** 检测用的查询**不许写死** ground-truth：注入的 step 窗（如 `step BETWEEN 150 AND 350`）、目标 rank、注入进程 PID，一个都不许进检测 SQL。检测器只能知道两件事：warmup 何时结束、到此刻为止看到的历史。**答案只有判分阶段能读。**

3. **冻结后不回头改。** 在 Loud（最强档）上把检测方案定稿后，**看了 Quiet / Masked 的结果也不许回来调** SQL / 阈值 / 判据。唯一例外：查出是环境 bug（表名变了、字段没了），修完**重跑一整轮探索再冻结**，并记录变更理由。

4. **旁证不升判分。** `injection.log`、裸 `pgrep <注入进程名>` 这类“**因为我知道答案才查得到**”的东西，只能当旁证写在备注里，**不许用来抬 D-level**。判分证据必须是工具接口本身（如 SQL 表、trace）能独立产出的。

5. **环境跑不起来记 N/A，不记 D0。** 对手工具在这个集群装不上 / 依赖不兼容 → 记 `ENV-BLOCKED`。这**不等于**“它检不出”（D0 是“执行了但没检出”）。不许把环境不兼容包装成 Probing 的优势。

6. **跑完立刻回拉本机。** 远端跑完或到关键里程碑，马上把结果拉回本机 `results/<node>/<run_id>/`（jsonl、run.log、配置快照、判分）。远端盘不可靠，别指望它长期在。

## 二、控制变量原则（五条，管“这么比对不对”）

红线管“你能不能这么做”，这五条管“你这么比较严不严谨”。每条三行：**想测什么 / 谁偷偷混进来 / 怎么隔离**。

**① step 之间不独立。**
- 想测：注入让训练慢了多少。
- 混进来：warmup 偏慢、checkpoint 那一步的尖峰、内存/GC 的累积——后面的 step 天然比前面慢，这个差里混了“时间流逝本身”，不全是注入。
- 隔离：健康基线用**独立的一条 run**，**不拿同一个 run 的“注入前段”和“注入后段”相减**；比较时**按 step 号对齐窗口**（基线的 150–350 比注入的 150–350），不拿注入窗去比全程平均；注入窗尽量避开 checkpoint 步，或保证两条线跨过的 checkpoint 数一样。

**② run 与 run 之间会漂移。**
- 想测：挂上工具的常驻开销（有工具比没工具多花的）。
- 混进来：几条 run 背靠背跑，机器热了、邻居作业上来了、缓存变了——后面那条慢可能是半小时后环境变了，不是工具。
- 隔离：**同 seed**（保证第 N 步喂的是同一个 batch）；尽量**同时段连着跑**；健康线**多跑几次确认稳**（step_time 变异系数 CV < 5%），不稳就先排查环境再比；结论看**中位数**不看单次。

**③ 一次性扰动 ≠ 常驻开销。**
- 想测：工具的持续采集开销 / 注入的稳态效果。
- 混进来：attach 那一下的卡顿、sidecar 启动时起进程和编显存的一次性开销——都是瞬态，不是稳态。
- 隔离：接入或注入后**丢掉头几步瞬态**，开销和效果**都只用稳态窗口**测。

**④ 同节点的 rank 会互相连累。**
- 想测：到底哪个 rank 是被注入的（定位 victim）。
- 混进来：同节点 rank 共享 PCIe / 内存带宽 / CPU，一个被咬全跟着慢；而且分布式同步点会让**所有** rank 一起等到最慢的那个。
- 隔离：定位看“谁的**本地计算**先慢”，**不是“谁的 step 慢”**（同步会让大家一起慢，看不出源头）；被注入的那个（culprit）和被它连累的邻居（victim）**分开记录**，别糊成一个。

**⑤ 观测动作本身会干扰被测量。**
- 想测：干净的 step_time。
- 混进来：一边测 step_time 一边狂跑 dump / 检测查询，查询开销混进了 step_time。
- 隔离：测开销那条线（有工具 vs 没工具）**别同时做重查询**；或记下每次查询的时机，分析时把受影响的 step 排掉。

> 还有别的坑（dtype、数据顺序、多节点时钟不齐……）以后遇到再往这里补，一条也是三行。

## 三、三阶段：每一步 Agent 该做什么

一个 case 从零到出数，走三段：**探索 → 正式 → 判分**。三段的边界就是纪律边界。

### 阶段一 · 探索（pilot）——找路，允许任何手段

**目标**：证明这个 case 在当前环境**能跑通**，并找到检测它的路。

**做什么**：
1. **小规模快跑**（短 iters / 单节点 / Loud 档），确认注入真的让 step_time 变化 **> 噪声**。变不动 → 调注入参数；调到最强还不动 → 这个 case 在当前配置下**不可咬**，记 `injection_ineffective`，不进分母。
2. **交互式查**工具接口，找出：哪些表 / 字段在**这个平台上真有值**（不许假设 SOP 写的表都在）、哪个信号能区分“注入期 vs 健康期”、阈值大概在哪。
3. **标定剂量**：注入强度要和机器规格挂钩（例：CPU 压力的线程数要相对核数**过载**才咬得动）。记下**实际生效**的参数，不一定是文档预写的值。

**这个阶段允许**：手动查、用 Agent 探、看 dashboard——**目标是“找到路”，手段不限。**

**产出**：一份 pilot 记录——注入生效性（变化比）、可用的表/字段清单、初步的检测查询序列 + 阈值、实际剂量。

**交接（进入阶段二前必须做的定稿动作）**：把探索到的检测路径**定稿成确定性脚本**（固定的查询序列 + 固定阈值 + 固定判据），写回该 case 文档。**这一稿就是“冻结”**——此后受红线 3 约束。冻结标准：在 Loud pilot 数据上能**稳定**到达预期 D-level。

### 阶段二 · 正式（run）——照冻结的方案跑，不再探索

**目标**：跑平行 run 对照，产出判分需要的原始数据。

**做什么**：
1. **跑前**：`ledger.md` 的环境门禁**必须全绿**（见下第四节契约）；确认这个 case 的探索已完成、方案已冻结。
2. **平行 run**：同一个 case 跑一组 run，**唯一变量是“挂哪个工具”**，其余（seed / 训练脚本 / 超参 / 注入器 / 注入时机）全固定。至少要有：无工具健康线、无工具注入线、挂 Probing 线；对手能跑就加，跑不起记 N/A。
3. **执行人不再交互探索**——**全跑冻结脚本**。冻结方案在某档检不出，就**如实记 D0**，不回去改（红线 3）。

**产出**：每条 run 的原始数据 + manifest（节点、commit、剂量、seed、world_size、ground-truth）。

### 阶段三 · 判分（score）——冻结规则给分，此时才准看答案

**目标**：用冻结的判分规则，给每条 run 定 D0–D5，产出统一结论。

**做什么**：
1. 跑冻结的判分脚本，对每个 case × 每个工具 × 每档，给出 D-level + 证据引用。
2. **判分阶段才允许读 ground-truth**（注入窗、target rank）——用来核验检测器报得对不对（红线 2 在这里解禁）。
3. 判错就如实记（红线 3：不回头改检测器）；`ENV-BLOCKED` 和 D0 分开记（红线 5）。

**D0–D5 固定含义**（各 case 统一，不许各自解释）：

| 级 | 含义 | 判定 |
|---|---|---|
| D0 | 无感 | 检测器输出“无异常” |
| D1 | 检出 | 触发了异常信号 |
| D2 | 时间窗 | 报告的异常窗 ∩ 真值注入窗 ≥ 50%（IoU≥0.5） |
| D3 | 对象 | 指出的 rank/host **等于**真值（通信类：victim 和 culprit 要分开，找到等待者≠找到源） |
| D4 | 根因层 | 输出的坐标（位置×来源）**等于**真值那一格 |
| D5 | 可处置 | D4 成立**且**执行处置后指标恢复（如连续 10 步回到注入前 ±10%） |

规则：**只取最高的连续正确级**（D3 对但 D4 错 → 记 D3）；“出个修复建议”不算 D5，**必须真执行动作并验证恢复**。

## 四、契约：规则与台账怎么勾住

- **进入阶段二（正式 run）之前**：读 [`ledger.md`](ledger.md) 的「环境」章，门禁清单**全绿**才开跑。门禁里具体有哪些条目、哪个集群会怎么崩——都在台账，不在这里。
- **跑完 / 改了配置之后**：回来更新 [`ledger.md`](ledger.md)——跑了哪个 case、什么档、挂了什么、到 D 几、run_id。**改动「全局固定」区的任何一格前先停**：那会让之前所有 run 变得不可比（见台账开头的维护纪律）。

## 附：自查清单（审阅这套规则、或审阅一份 case 方案时对照）

- [ ] 检测 SQL 里**没有**写死的 step 窗 / target rank / PID？（红线 2）
- [ ] 环境相关的东西（集群名、镜像、会崩的坑）**都在台账、没漏进本文件或 case 检测方案**？
- [ ] 开销比较用的是**独立健康线**、**同 seed**、**对齐窗口**、**中位数**？（控变 ①②）
- [ ] victim 和 culprit **分开记**了，没把“一起慢”当成“都是源”？（控变 ④）
- [ ] 冻结之后的改动，**只发生在查出环境 bug 时**，且记了理由？（红线 3）
- [ ] `ENV-BLOCKED` 和 D0 **分开**，没混为一谈？（红线 5）
